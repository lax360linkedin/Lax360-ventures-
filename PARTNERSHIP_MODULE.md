# Partner With Us: franchise and partnership module

Built locally. Nothing deployed, committed or pushed.

## Architecture
* **Public pages (frontend):** 17 routes, all prerendered (own title, description, canonical, Open Graph, breadcrumbs, one H1) and in `sitemap.xml`: `/partner-with-us`, `/franchise`, `/authorized-partner`, `/referral-partner`, the nine `/{franchise|authorized-partner|referral-partner}/{education|digital-marketing|it}` pages, `/partner-with-us/apply`, `/faq`, `/privacy-policy`, `/terms-and-conditions`. Built-in content is original LAX360 copy in `src/data/partnership.js`; each of the nine pages has its own text, lists, responsibilities, policies and FAQs (division-specific content inside a type-specific frame). Direct URLs, refresh and back/forward work because the pages are static files (Vercel serves them first; an unknown path under these prefixes is a real 404).
* **Admin overrides (backend):** `GET /api/public/partnerships` returns, in ONE request, what an administrator has changed (headings, introductions, extra sections, hidden sections, SEO, commercial fields marked published, hero image, brochure, FAQs, published policies, portal link). The pages render fully without it, so a sleeping backend never blanks them.
* **Applications:** `POST /api/public/partnerships/applications` validates server-side, strips markup, stores in PostgreSQL, writes a history entry, returns a unique reference (e.g. `LAX-FE-261125-CF0A11`) only AFTER the commit, and e-mails the team / applicant in the background when SMTP is configured (a failed e-mail never fails the application). Honeypot, per-address rate limit (6/hour), a same-person duplicate returns the same reference. **An application never creates a partner account.**
* **Admin (Partnerships section, permission `partnerships`):** Overview (real counts and charts), Applications & enquiries (search, filters, 11-status workflow, notes, follow-ups, assignment to staff and branch, history, CSV export that neutralises spreadsheet formulas), Opportunity pages (content, hero image and brochure from the media library, sections shown, extra sections, per-field commercial publish, SEO, publish/noindex), FAQs, Policies & agreements (versioned; draft never public; publishing needs a named reviewer and archives the previous version), Settings (accept applications, notification e-mails, partner portal https link, general brochure). Writes are rate limited and audited (`partner.*`).
* **Database:** migration `0028_partnerships` (additive: `pt_applications`, `pt_application_events`, `pt_pages`, `pt_faqs`, `pt_policies`, `pt_settings`; RLS on; rollback `alembic downgrade 0027`).

## Content awaiting management or legal review
All franchise commercial fields (fees, investment, deposit, royalty, revenue sharing, agreement length, renewal, territory, exclusivity, refund and exit) show “available upon consultation” until published in the admin. No policy text is published: the privacy and terms pages say what applies meanwhile. The built-in policy summaries on each page (and the public summary of the authorized/referral commercial model: first valid lead, verification, product- and deal-based commission, monthly settlement, no minimum, manual bank/UPI, early withdrawal of the whole eligible balance, refund adjustment) are wording of the rules you gave me and need your approval before launch. Business-setup, classroom, lab and staffing requirements on the franchise pages are indicative, not approved specifications.

## Not done / limitations
* **No photographs:** I cannot source licensed business photography here, and I did not want to pass stock or generated images off as LAX360 premises or staff. Heroes use typographic gradients; each page accepts a real hero image in the admin (alt text required).
* **Multilingual:** the pages use the site's existing translation mechanism, but the new English text has no Tamil/Hindi translations yet (it falls back to English); translations of legal/commercial text must be reviewed before publication.
* **Branch-restricted access:** the permission is all-or-nothing. A branch user cannot be limited to their own branch's applications without a larger permission change (needs your approval); assignment and branch fields exist.
* **Not built:** brochure download counts, notification templates for each status change (only new-application and acknowledgement e-mails exist), a per-page view analytic ("most viewed opportunity"), the public Partner Management Portal (the portal link is configurable only).
* **Source page** on an application is the page where it was submitted (the apply page); the type and division chosen are stored separately.
* The reference websites were read for structure only (section headings and form fields); nothing was copied.

## Partner With Us header CTA and dynamic menu
* **Header:** "Partner With Us" is no longer in the main navigation. It is a highlighted gradient button beside Login (`components/layout/PartnerMenu.jsx`). The label links to `/partner-with-us`; hover or keyboard focus opens a dropdown of the three programs; hovering a program opens a nested side menu of its divisions; every item links straight to its page. The chevron button toggles it for touch and keyboard (aria-expanded, Arrow keys, Escape). Below 1280px the CTA shows the icon and chevron only, below 1536px the label is "Partner", and the header grid is `auto / 1fr / auto` so the nav, CTA and Login never overlap (checked at 1024, 1280, 1440). Phones and tablets (< 1024px) use an expandable accordion in the mobile menu.
* **Dynamic:** table `pt_menu_items` (category, slug, label, description, order, enabled, built-in). Public `GET /api/public/partnerships/menu`; admin screen **Partnerships > Navigation menu** (add, rename, describe, reorder, show/hide, remove; max 12 per program). The built-in three divisions can be hidden or renamed, never deleted. An added entry gets its own page `/{program}/{slug}` (client-rendered from the payload's `custom_pages`; text, image, FAQs, SEO editable under Opportunity pages), appears in the dropdown, the program page, the division switcher and the application form, is accepted by the application API, and is in `sitemap-content.xml` while enabled and indexable. Removing an entry deletes its page content; received applications are kept.
* **Migration 0028 was edited in place** (never applied anywhere): it now creates 7 tables including `pt_menu_items`, and the application division CHECK was dropped (the division is validated against the live menu). If 0028 had already been applied somewhere, a new migration is needed instead; tell me.
* **Deployment notes:** `vercel.json` gained rewrites for `/franchise|authorized-partner|referral-partner/:slug` so admin-added pages load (an unknown well-formed slug shows the site's not-found view with HTTP 200, the same soft-404 behaviour accepted for other dynamic routes). A header override saved in the admin (Navigation) may still list "Partner With Us"; the header and mobile menu now filter it out. The menu shows the built-in list instantly and the live list after the first open (cached 5 minutes), so a sleeping backend never breaks it.
* **Tests run:** backend `test_partnerships.py` and `test_partnership_menu.py` (22 passed), build, SEO audit, link audit, routing check (25 rewrites), client tests. Browser (dev server): header measurements at 1024/1280/1440, hover dropdown and nested flyout, a simulated admin-added division showing in the flyout, mobile accordion and its page. **Not run:** the admin screen against a live backend, real PostgreSQL, iOS devices, Tamil/Hindi, dark/purple theme screenshots of the dropdown (it uses the same theme tokens as the rest of the header; only the light theme was viewed).
