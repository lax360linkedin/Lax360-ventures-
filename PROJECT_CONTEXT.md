## 1. Standing rules (the owner's decisions — follow them)
1. **The owner does ALL Git.** Never commit, push, branch, stash or deploy. Edit local files freely without asking.
2. **No production database writes, migrations, deploys or credential changes without explicit approval.** Port **8000 is the owner's real backend connected to the real Supabase database**: never write to it for testing. A command that overwrites admin-edited production content (for example `refresh-upcoming --apply`) is blocked by the safety classifier; do not work around it, ask.
3. **Test on isolated servers only**: an in-memory SQLite demo backend on port **8012** (script pattern in section 11) and a temporary `.claude/launch.json` config `lax360-demo` for the frontend on port **5176**. Restore `launch.json` afterwards. Start the demo backend with `APP_ENV=test` so the public cache does not read the real database. Do not kill python processes in general; stop only the process you started (check by port).
4. **Honest content only.** No invented clients, results, prices, launch dates, availability or product capabilities. Planned things say so ("Under Development", "Coming Soon"). Samples are flagged `is_sample`.
5. **Preserve** design, theme, animations, functionality, SEO, URLs, redirects, Admin Panel, DB records, Google Sheets integrations, auth and security in every change. Never expose secrets.
6. **Never claim a test passed that was not run.** Backend tests need PostgreSQL (see section 11); say so when they were not run.
7. Keep user-facing explanations plain and short; the owner is not a developer. Always report what was NOT verified.

## 4. Core architecture patterns
- **CMS content kinds** (`backend/app/services/content_service.py`, `KINDS`): each kind = label, group, module permission, `fields` (via `F(...)`). The admin UI is generated from `KINDS`. Items live in table `content_items` (kind, slug, title, data JSON, status draft/published, sort_order). Public API `/api/public/content-all` returns every published item per kind (images resolved to URLs).
- **Built-in first, database after migration**: the frontend ships built-in copy (prerendered, never empty). `python -m app.cli migrate-content` copies it into the database (backup first, additive, never overwrites) and marks a domain via a `content_seed` item; hooks `useDatabaseItems(kind, domain)` then use the database as the only source. Domains migrated in production: network, upcoming, divisions, courses, partner-products.
- **Public response cache** `backend/app/core/pubcache.py`: in-process, TTL 15 s + stale 300 s, single-flight builds, rebuild on admin save (`bump()` on commits of watched models), keep-warm thread. Endpoints wrapped: `/public/site`, `/public/content-all`, hero video, partnerships, partnerships/menu, redirects. With `APP_ENV=test` caching is off.
- **Client cache**: `frontend/src/services/siteService.js` keeps the last public data in localStorage and refreshes in the background (a second reload may be needed to see an admin change).
- **Settings** (`settings_service.py`): whitelist `SPEC` of key/value site settings; Super Admin only keys in `SUPER_ONLY_KEYS` (`site_theme`, `custom_themes`).

## 5. Service structure (approved hierarchy)
- **Three ACTIVE divisions**: Software & IT Services (`software`), Digital Marketing (`growth`, public address `/services/digitalmarketing`), Education & Training (`education`).
- Headless SaaS & API Solutions, AI Workflow Automations & Integrations, Mobile & Business Applications are **sub-sections of Software & IT Services**, not divisions. Software has 13 headline sub-services (list in `frontend/src/data/services.js`) plus e-commerce and the carried sub-services. Existing page addresses are kept (a renamed sub-service keeps its old slug; `OFFERING_SLUG` in `utils/slugify.js`).
- **Four UPCOMING divisions** (status Under Development, interest registration only, no dates/prices): Artificial Intelligence (`/artificial-intelligence`, slug `ai`), IoT, Embedded Systems & Robotics (`/robotics`), CAD Designing & Training (`/cad-engineering`), Blockchain & Web 3.0 (`/blockchain`). The upcoming AI division is distinct from the live AI Workflow Automations. The CADPOINT education partnership stays ACTIVE under Education & Training.
- Old addresses `/services/{ai,headless,automation,mobile}` and their offering pages redirect (client route + 111 permanent redirects in `vercel.json`, all locales).
- **Active divisions are database-driven** (kinds `division` and `division_service`, seeded from `backend/app/seed_data/divisions.json`, generated from the built-in data). Hook `frontend/src/hooks/useDivisions.js` (`useDivisionTools()` → `divisions`, `allDivisions`, `getDivision`) overlays the database on the built-in copy; empty fields fall back to built-in text. Admins can add/rename/reorder/hide/delete divisions and sub-services and move a sub-service by changing its division. The Services page keeps bespoke layouts for the three built-in divisions plus Headless/Automation/Mobile sections; a new division gets a generic section and `GenericHero`.
- **Upcoming divisions are database-managed** (kinds `upcoming_category`, `upcoming_service`; `frontend/src/hooks/useUpcoming.js`). Built-in source: `frontend/src/data/upcomingServices.js` and `backend/app/seed_data/upcoming.json`. The AI division shows from built-in copy until the database has it (`ADDED_LATER`). Statuses: coming_soon, under_development, available (= live), unavailable. Changing a status to Available in the admin activates it everywhere.
- Contact form service catalog `backend/app/contact_catalog.py` and testimonial/SEO scope list `backend/app/service_pages.py` use ids `software/<slug>`, `growth/<slug>`, `education/<slug>` (always `growth`, never `digitalmarketing`, in ids).

## 14. Decisions log (why things are the way they are)
- Content in the database with built-in fallback so the site is never empty and prerender/SEO keep working.
- Upcoming/active divisions share `ContentItem` kinds so one generic admin UI manages them; moving a sub-service = changing its `division` field.
- Old URLs are never removed: redirects instead (SEO). Renamed sub-services keep their slug.
- Admin account creation runs in a background thread so a slow database never delays server start (hence tests must poll).
- Theme tokens are CSS variables; custom themes generate CSS in the browser to avoid redeploys and avoid a flash with a cached copy applied before first paint.
- Header fit uses measurement rather than fixed breakpoints because menu labels, language, admin-edited menu and login state change widths.
